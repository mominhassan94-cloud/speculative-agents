# Testing speculative tool execution where it matters

**The class project should test one narrow, falsifiable claim: for read-only tool calls, exact-match speculation saves wall-clock time in proportion to the speculator's hit rate, capped by the actor's think time, at a measurable waste cost, with zero change to the agent's observations or the world state.** Prior work supports the idea but leaves the part a class project can do better. Speculative Actions reports up to about 20% lossless latency reduction at 22-55% prediction accuracy, and PASTE reports up to 43.5% lower task time on workloads with slow tools. Neither reports a wasted-call rate, variance, or confidence intervals. The repo's first results (rules and oracle both 20-32% faster on three tasks) are real but not yet evidence: the rule speculator is hand-written against the same plans it is scored on, the scripted agent never deviates, so `wasted` is zero on every row, and savings are capped by a 0.15 s scaled think time. The highest-value work is therefore (1) fixing the statistics and metrics, (2) validating the analytical latency model with a controllable-accuracy oracle and think-time sweeps, (3) replacing hand-written rules with a speculator mined from held-out data, and (4) testing safety as an adversarial property (stale hits, early side effects, injection canaries) instead of reporting that nothing broke. Replaying public trajectories (tau-bench first) can supply realistic hit-rate numbers cheaply, but replay cannot measure end-to-end speedup without a latency model. Source quality is mixed: most paper figures below were read through a fetch tool's page summary, several 2026 papers only through search snippets, and the latency table is the research team's own estimates. Section 5 lists the weak spots.

## What the literature establishes, and how much to trust it

Speculative Actions (Ye et al., arXiv 2510.04371) pairs a fast speculator with a slow actor, pre-launches the guessed next action, and commits only on match. It reports **19.5% average time saved at 54.7% accuracy with three chess predictions**, **22-38% of tau-bench retail API calls predicted correctly**, and **up to 46% top-3 accuracy on HotpotQA** with strict function-plus-argument matching ([arXiv](https://arxiv.org/html/2510.04371v2)). Its theory is the most reusable piece: with exponential latencies the runtime ratio tends to 1 - [p/(1+p)][alpha/(alpha+beta)], so even a perfect speculator cuts at most half the runtime ([arXiv](https://arxiv.org/html/2510.04371v2)). Two of its three lossless environments (e-commerce, HotpotQA) report only prediction accuracy, not measured latency, so the 20% headline rests on chess alone.

PASTE (Sui et al., arXiv 2603.18897) is the closest design to this project, because it speculates tool calls rather than game moves. It mines recurring tool-call contexts (tool type plus success or failure) from historical traces, infers argument mappers (for example, the URL of a fetch is the first URL in the preceding search output), keeps patterns above an empirical confidence, and holds speculative results outside session state until an authoritative call matches by canonicalized name and arguments ([arXiv v3](https://arxiv.org/html/2603.18897v3)). Reported results are up to **43.5% lower average task completion time and 55.4% lower p99**, with **top-1 accuracy of only up to 27.8% and top-3 recall up to 43.9%** ([arXiv v3](https://arxiv.org/html/2603.18897v3)). The 93.8% "hit rate" counts any of several speculated candidates, so it is not comparable to top-1. The paper audited more than 20,000 speculative actions, blocked 602 potentially side-effecting ones, and found no changed final results ([arXiv v3](https://arxiv.org/html/2603.18897v3)). Its ablation matters for our design: blind tool-only speculation took 419 s versus 342 s for an LLM-side-only variant and 270 s for the full system, so unthrottled speculation can hurt.

LLMCompiler and ReWOO are a different category. LLMCompiler plans a dependency graph and runs independent calls in parallel, reporting up to 3.7x latency speedup versus ReAct ([arXiv](https://arxiv.org/abs/2312.04511)); ReWOO decouples reasoning from observations for token efficiency ([arXiv](https://arxiv.org/abs/2305.18323)). Neither guesses, so neither wastes calls, and both are valid non-speculative baselines: if two calls are independent and known up front, parallelism beats speculation. Speculation earns its keep only on dependent chains (search then open the top result) where the next argument depends on a result the agent has not yet reasoned over.

The 2026 literature widens the picture but is weaker evidence. SPORK reports that tool names are predictable from the model's own first token (74.6-99.6% across five benchmarks on Qwen3-32B) while exact arguments are not (7.6-83.9%), and that gating at a 0.90 confidence threshold gave 88% precision ([arXiv 2607.03333](https://arxiv.org/html/2607.03333)). Its speedups are modest (mean 1.09x to 1.18x on tau2) and it runs slower (0.79x) when the actor does not think first. TomasuLLM reports 1.27-1.35x speedups with zero false accepts across 4,010 audited commits ([arXiv](https://arxiv.org/abs/2609.38201)); AOSpec reports 11.8-32.5% mean latency reduction on Terminal-Bench ([arXiv](https://arxiv.org/abs/2608.00881)). A single-author practitioner blog found the opposite on GAIA: GPT-5-nano as speculator hit 18.2% and 10.5% on levels 1 and 2, and mean latency got worse (173.8 to 184.1 s on level 1) ([blog](https://yogesh.bearblog.dev/speculative-tool-calling/)). That negative result is not peer reviewed, but it matches PASTE's ablation and predicts exactly the failure regime this project should map: low hit rate, short tool-idle time, and tools too fast to hide.

The tool-latency premise holds, with caveats. PASTE attributes 45-57% of agent end-to-end latency to tool execution without queueing ([arXiv v3](https://arxiv.org/html/2603.18897v3)), while a synthetic multi-agent study with simulated delays found only about 9% in tool I/O ([arXiv 2606.19382, via search summary](https://arxiv.org/abs/2606.19382)). The tool share is workload-dependent, so the project should treat it as a swept parameter and not an assumption.

## The repo's first results are think-time bound and not yet a test of prediction

The checked-in run (`workspace/results/eval_20261110_030857.csv`, three reps, `--scale 0.1`, `--think 1.5`) shows rules cutting `flights_compare` from 1.43 s to 0.97 s (**32% faster**) and `web_read_all` from 1.05 s to 0.92 s (12%), with no change on `vague` `trip_prep` (rules never fire), while the oracle gets 23% on `web_read_all` and 20% on `trip_prep`. Three facts limit what this shows. First, `RuleSpeculator` in `speculator.py` encodes "after `search_flights`, fetch the first nonstop fare; after `search_web`, open the first result" against the same scripted plans in `tasks.py`, so on `flights_compare` and `book_cheapest` it ties the oracle (3 of 3 hits, 0 waste). It is a second oracle, not a speculator, and its 100% precision says nothing about generalization. Second, the 0.46 s saved on three hits equals about 3 x min(T, D) with scaled T = 0.15 s and D = 0.15 s, which is the think-time cap predicted by the per-step model min(T, D - s) (inference; derived by the notes' author from the Speculative Actions bound). Any headline percentage quoted without a `--think` sweep is an artifact of that one constant. The notes' own estimate is that a Sonnet-class tool-calling step runs several seconds while the mock's 1.5 s is closer to a Haiku-class step, and that mock tool latencies are uniform with a thin tail whereas published web-search p95 is about 1.5-2x the median ([HackerNoon SERP benchmarks](https://hackernoon.com/lite/serp-benchmarks-success-rates-and-latency-at-scale), [fastCRW](https://fastcrw.com/benchmarks/tavily-search)). Those estimates are the team's inference, not measurements. Third, `blocked` is nonzero only for the oracle on `book_cheapest`: the safety gate has been exercised by one speculator on one task.

Reading `runtime.py` against the safety literature exposes gaps that the harness cannot currently detect (all of this is inference from the code and the hazard lists in the notes). The cache key is `tool|json.dumps(args, sort_keys=True)`, so there is no argument canonicalization beyond key order. Entries have no TTL and are never invalidated when a write tool executes, so a speculative `search_flights` result computed before a `book_flight` can be served after it if the arguments match, which is exactly the read-after-write hazard. Unconsumed pending futures are never evicted, `wasted` is only `launched - hits`, and there is no per-call event log, no precision/recall, and no wasted tool-seconds. `observe()` returns early on an empty history in the speculators, so the first call of every task is never prefetched; that is a design axis (task-prefix speculation) worth naming even if the project leaves it out. `run_eval.py` runs modes in fixed order within each rep and prints means only, so warm-up order effects and variance are invisible.

## Speculator designs worth comparing, from cheapest to most ambitious

The comparison should be a ladder in which each rung answers a question the previous one cannot. A **random** speculator (a valid read-only call drawn from the tool set) and an **always-speculate** setting (threshold 0, gate on) are floors and show the cost of unthresholded guessing; the notes' author proposes these, and the papers do not name them. The existing **rules** mode is kept but relabeled as a hand-coded oracle-adjacent baseline. The real cheap baseline is a **pattern-mined speculator** in the PASTE style: key on (last tool, last status) with back-off from order 2 to order 1, store next-tool counts, and learn argument sources by searching earlier results in the same trace for each argument value and recording the path (for example `results[-1].results[0].url`), keeping a template only if it reproduces the argument in a high fraction of occurrences. PASTE found that 95% of web-visit URLs are strict substrings of the preceding search output ([arXiv v3](https://arxiv.org/html/2603.18897v3)), which is why a dataflow template is plausible here. The notes suggest an 80-90% reproduction threshold; that number is a guess. Next comes an **LLM speculator** (`LLMSpeculator` or `GeminiSpeculator`, already in `speculator.py`) with two cheap upgrades: instruct it to copy argument values only from strings in context and reject any candidate whose argument string is not a substring of the history, and ask for top-k candidates with a verbalized confidence that is then calibrated on logged hit/miss data (isotonic or Platt). Claude does not expose token logprobs, so agreement across a few sampled guesses is the alternative confidence signal; no paper compares the three signals inside an agent loop, so any result here is new. A **hybrid** (pattern speculator when its empirical confidence clears a threshold, LLM otherwise) fits PASTE's finding that patterns work on structured loops and fail on open-ended research. A **self-speculation / streaming early-dispatch** variant is a stretch goal: SPORK and the joint-RL paper show the actor's own context predicts best ([arXiv 2607.25816](https://arxiv.org/html/2607.25816)), and Anthropic's fine-grained tool streaming emits tool-input JSON fragments before the call completes ([docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/fine-grained-tool-streaming)), so a read-only call could be dispatched once its name and complete arguments stream in. That variant has zero prediction error because the arguments are the actor's own, and it saves only the generation tail, so it must be reported separately from true prediction. Finally, an **LLMCompiler-style parallel** baseline (issue all independent read-only calls of a step concurrently) shows what speculation adds over free, lossless parallelism.

The matching rule should stay exact for the headline claim, with a tiered extension reported separately: Tier 0 exact match after canonicalization (sorted keys, normalized URLs and paths, defaults filled), Tier 1 opt-in semantic match on free-text arguments only. The practitioner blog's relaxed-match experiment (cosine 0.8 gave a high cache rate with reduced accuracy) is the only evidence for the trade-off and is weak ([blog](https://yogesh.bearblog.dev/speculative-tool-calling/)); the project's lossless claim applies only to Tier 0.

## Datasets and replay: cheap, but replay measures prediction, not speedup

Replay evaluation takes recorded trajectories, runs the speculator on every prefix, and scores whether the predicted call equals the recorded next call, at zero tool-execution cost. The best fits, in order, are as follows. tau-bench ships `historical_trajectories` for airline and retail from two models (gpt-4o, Claude 3.5 Sonnet new) under an MIT license ([repo](https://github.com/sierra-research/tau-bench)); Speculative Actions already used tau-bench retail, whose 15 APIs split into 7 write and 8 read-only, giving a ready-made gate test ([arXiv](https://arxiv.org/html/2510.04371v2)). `Salesforce/APIGen-MT-5k` adds 5,000 tau-style multi-turn trajectories with explicit `function_call` and `observation` turns, but it is CC BY-NC 4.0 and partly GPT-4-generated, so use it for volume and not for redistribution ([Hugging Face](https://huggingface.co/datasets/Salesforce/APIGen-MT-5k)). `nebius/SWE-agent-trajectories` has 80,036 trajectories under CC-BY-4.0 with pass/fail targets, good for read-heavy coding traces where grep and open precede edits ([Hugging Face](https://huggingface.co/datasets/nebius/SWE-agent-trajectories)). ToolBench with StableToolBench's response cache gives deterministic API replay at breadth ([StableToolBench](https://github.com/THUNLP-MT/StableToolBench)), and Mind2Web is an optional web-action case ([Hugging Face](https://huggingface.co/datasets/osunlp/Mind2Web)). Skip TheAgentCompany and MCP-Universe as primary sources because they need Docker or live services.

Three limits apply. Replay only scores "predicted equals recorded"; it cannot say what a wrong speculative call would have returned, so end-to-end speedup from replay needs the latency model with per-tool-class latencies, not real execution. Recorded trajectories come from agents that were not speculation-aware, and their next calls are conditioned on real results. Fractions of read-only calls per task were not measured in any source, so the project must compute them (classify tau-bench tools by name prefix and verify against its `tools/` directory; that classification is unverified in the notes). The notes also found no released traces for PASTE, TomasuLLM, AOSpec, or Speculate with Memory, so there is nothing to reproduce directly, and Speculative Actions' repo bundles only chess trajectories ([GitHub](https://github.com/naimengye/speculative-action)).

## Safety and losslessness need explicit tests at three levels

"Lossless" in the literature means the final trajectory matches sequential execution, enforced by keeping speculative results out of authoritative state until a matching real call ([arXiv](https://arxiv.org/html/2510.04371v2), [arXiv v3](https://arxiv.org/html/2603.18897v3)). The harness's current checks (the `correct` answer flag and `side_effect_early`) cover only the weakest level. The notes' author proposes three: outcome-lossless (answer equivalent to baseline), trajectory-lossless (the agent-visible transcript of real calls and observations is identical across modes, tested by hashing it), and world-state-lossless (a snapshot of mock state, including ledgers and logs, identical across modes). Staleness belongs in the definition: a hit is lossless only if it equals what a fresh call at use time would return, which a shadow re-execution can verify.

Read-only does not mean safe to run early, and the speculation papers do not quantify most of the hazards (inference by the notes' author). Cached values go stale; a write between speculation and use invalidates dependent reads even on an exact argument match; discarded calls still consume quota and per-call billing; a "read" may append to an audit log or advance a pagination cursor; and per-user keys are needed to prevent cross-session leakage. The MCP specification treats tool annotations as untrusted hints unless the server is trusted, with pessimistic defaults (`readOnlyHint=false`), and says clients should not base decisions on annotations from untrusted servers ([MCP spec](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)); the project's `read_only` boolean should be the whitelist, treated as trusted because the team authors the mock tools, and missing flags should mean unsafe. Security adds an angle no paper studies directly: the speculator reads prior tool output that may be attacker-controlled, so speculation can fetch attacker-chosen URLs before the agent or user chose them, and a discarded fetch can still exfiltrate. Ghost Tool Calls argues that speculative calls leak intent even when abandoned and that only issue-time policies (altering or suppressing arguments or destinations before dispatch) help, not post-hoc filters or read-only restriction ([arXiv 2606.02483](https://arxiv.org/abs/2606.02483); abstract-level source). An argument-provenance rule (speculate only on argument strings that appear verbatim in the user prompt or prior trusted output) is the simplest issue-time policy and falls directly out of the substring check recommended above.

## Hypotheses, metrics, and the experiment plan

The metrics follow the notes' proposals. Time: end-to-end seconds per run, paired per (task, rep) against baseline, summarized as geometric-mean speedup of T_mode / T_base with a bootstrap 95% CI resampling tasks then reps, plus median and p95. Speculation quality: launched, hits, precision = hits / launched, recall = hits / real read-only calls, any-hit per step, and top-1 versus any-of-k reported separately because PASTE's figures use different denominators. Cost: wasted calls, wasted tool-seconds, extra billed tool units, speculator tokens and dollars (Haiku 5.5 is priced at $0.10 input and $0.50 output per million tokens against $2 and $10 for Sonnet 5.5, so a speculator call is roughly 1% of an actor step by the notes' worked example ([Anthropic pricing](https://platform.claude.com/docs/en/about-claude/pricing)); that ratio is an estimate that assumes 2,000 input and 100 output tokens). Correctness: pass rate and the three lossless levels above, plus the stale-hit count. Efficiency: fraction of oracle savings captured. Statistics: LLM agents are noisy even at temperature 0 (a 60,000-trajectory SWE-bench study found single-run spreads of 2.2-6.0 points and about 9 runs per agent to detect a 2-point gain ([arXiv 2602.07150](https://arxiv.org/html/2602.07150v2))), but the scripted brain has only timing noise, so 20 or more reps per cell are cheap; use at least 10 reps for live-LLM cells.

The hypotheses below are written so the harness can falsify each one. The "expected" column is the team's inference, not a published result.

| ID | Hypothesis | How the harness falsifies it | Expected |
|---|---|---|---|
| H1 | Per-step saving on a hit is min(T, D - s); whole-run speedup follows p x min(T, D - s) | Oracle with each guess corrupted with probability 1-p, p in {0.25, 0.5, 0.75, 1}, crossed with `--think` and `--scale` sweeps; fit measured saving against the model | Linear in p, flat in T once T exceeds D - s; mismatch means contention or timing bugs |
| H2 | Speculation is net-negative when T is smaller than speculator latency s, or when think time D is near zero | Same sweep with a simulated speculator delay s; look for ratio above 1 | Break-even at small `--scale` (fast tools) and at D close to s |
| H3 | Hand-written rules do not generalize: hit rate drops sharply on held-out tasks | Write 10+ new tasks with different tools or ordering; score rules, mined n-gram, and LLM on held-out set only | Rules fall well below their 100% on current tasks; mined speculator beats rules held-out |
| H4 | A mined pattern speculator gets top-3 hit rate in the 40-70% range on templated tasks and near zero on open-ended ones | Replay on tau-bench trajectories plus the vague task group | Prior range of 50-70% structured / 20-45% open-ended is the notes' guess, calibrated by PASTE (up to 43.9% top-3) |
| H5 | An LLM speculator's tool-name accuracy exceeds its full-call exact-match accuracy by roughly 3x | Live Haiku/Gemini run on the task set, logged per step | Name accuracy high, exact args low unless the substring rule is applied |
| H6 | Confidence thresholding raises precision and lowers waste at a small cost in time saved | Threshold sweep 0 to 1; plot precision, waste, and speedup | Pareto knee near the SPORK-style high threshold; always-speculate shows more waste |
| H7 | The safety gate allows zero early side effects, even under an adversary | New `always-side-effect` speculator guessing every write tool at confidence 1.0 | `side_effect_early` false in all runs; `blocked` equals guesses |
| H8 | The current runtime can serve a stale hit after an intervening write (an expected failure) | Hazard task: read, then mutate the same resource, then real read with identical args | Stale hit served today; passes only after scope-versioned invalidation |
| H9 | Agent-visible transcripts and final mock-world state are identical across all modes | Hash the real-call transcript and snapshot mock state per run, compare to baseline | Identical for Tier 0; differences appear only when relaxed matching is on |
| H10 | An injection canary in a search result is fetched speculatively unless argument provenance is enforced | Canary URL in a mock search result; count speculative fetches of it | Fetched by naive speculators; blocked by the provenance rule |

## Conclusion

The literature's real gap is not another accuracy number but honest accounting: no anchor paper reports waste, variance, or staleness, which are exactly the quantities a mock-tool harness with a scripted agent can measure cleanly and cheaply. That reframes the project's contribution from "speculation saves time" (already shown, and bounded by think time and speculator latency) to a map of when it pays: the (hit rate, tool latency, think time, speculator latency) region where it wins, the region where it loses, and a safety result that survives an adversarial speculator and a stale-cache attack. The existing README promise of a time-saved-versus-wasted-calls chart is achievable once precision, wasted seconds, and a threshold sweep exist, and the oracle-gap curve (fraction of oracle savings captured) is the cleanest single figure for comparing designs.

Two cautions shape the next steps. The current rules-versus-oracle tie is a warning that the evaluation has no held-out signal, so the held-out split and a mined speculator should be built before the task count grows. And the strongest honest sentence the project can currently write is conditional: with exact-match, read-only-only speculation, savings follow hit rate times min(tool latency, think time minus speculator latency), and that model is testable in an afternoon with a corrupted oracle.
